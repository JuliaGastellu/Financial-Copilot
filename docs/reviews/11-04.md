# Revisión de Código: Financial Copilot

## Visión General

Proyecto backend en **FastAPI + SQLModel + LangChain** que implementa un copiloto financiero personal con RAG, motor de oportunidades y chat con IA. Arquitectura bien estructurada con separación clara en capas (rutas, servicios, modelos, schemas, AI/RAG).

---

## 1. Seguridad

### Problemas encontrados

**`python-jose` está sin mantenimiento** (`backend/app/core/security.py:6`)

- La librería `python-jose` no recibe actualizaciones. La recomendación es migrar a `PyJWT` (aka `pyjwt`), que es mantenida activamente.

**Secret key con valor por defecto funcional** (`backend/app/core/config.py:17-19`)

```python
secret_key: str = Field(
    default="clave_desarrollo_cambiar_minimo_32_caracteres_xx",
    min_length=32,
)
```

- Si no se configura `.env`, la app arranca con una clave predecible. Sería más seguro no tener default y que la app falle si no hay clave configurada, o al menos validar que no sea el default en producción.

**Token de acceso con expiración de 7 días** (`config.py:21`)

```python
access_token_expire_minutes: int = 60 * 24 * 7  # 10,080 min
```

- Es excesivamente largo para un JWT sin mecanismo de revocación. No hay endpoint de logout ni blacklist de tokens.

**Sin rate limiting en endpoints de autenticación** (`backend/app/api/rutas/auth.py`)

- Los endpoints `/auth/login` y `/auth/registro` no tienen protección contra fuerza bruta.

**Sin validación de complejidad de contraseña** (`backend/app/schemas/auth.py:10`)

- Solo se valida `min_length=8`. No hay requisitos de caracteres especiales, mayúsculas, etc.

## 2. Bugs y Problemas de Código

**Variable `or_` hace shadowing de SQLAlchemy** (`backend/app/services/matching_oportunidades.py:46`)

```python
ur = _orden_riesgo(perfil.nivel_riesgo_percibido)
or_ = _orden_riesgo(op.nivel_riesgo)  # <-- shadowing sqlalchemy.or_
```

- `or_` es el nombre de la función `or_` de SQLAlchemy. Aunque aquí no se importa directamente, es confuso y propenso a errores. Renombrar a `op_r` o `riesgo_op`.

**`datetime.utcnow` está deprecado en Python 3.12+** (múltiples modelos)

En `backend/app/models/user.py:18`, `financial.py`, `analysis.py`, `market.py`, `knowledge.py`:

```python
created_at: datetime = Field(default_factory=datetime.utcnow)  # deprecated
```

Ya usan `datetime.now(UTC)` correctamente en `security.py`, pero los modelos siguen con `utcnow`. Deberían usar:

```python
from datetime import UTC
created_at: datetime = Field(default_factory=lambda: datetime.now(UTC))
```

**Docstring inconsistente en retriever** (`backend/app/rag/retriever.py:41`)

```python
"""Devuelve lista de (contenido, distancia; menor es mejor en pgvector `<->`)."""
```

Pero el SQL usa `<=>` (distancia coseno), no `<->` (distancia L2). El operador en el código es correcto, pero la documentación no coincide.

**Migración inicial frágil** (`backend/alembic/versions/001_inicial.py:23`)

```python
def upgrade() -> None:
    op.execute(sa.text("CREATE EXTENSION IF NOT EXISTS vector"))
    SQLModel.metadata.create_all(bind=op.get_bind())
```

Usar `create_all()` en Alembic anula el propósito de las migraciones incrementales. Cuando se agreguen tablas futuras, `create_all` intentará recrear todo. Lo correcto es usar `op.create_table(...)` para cada tabla.

## 3. Arquitectura y Diseño

### Cosas bien hechas

- Separación limpia en capas: `api/rutas`, `services`, `models`, `schemas`, `ai`, `rag`
- Patrón de proveedor abstracto para mercado (`MarketDataProvider`) permite extensibilidad
- Disclaimers financieros en los prompts del sistema -- responsabilidad legal
- RAG con deduplicación por hash SHA-256 para evitar re-ingesta
- Fallback SQLite/pgvector para tests vs producción
- Structured output de LangChain con Pydantic (`SalidaAnalisisJson`)
- Docker con healthcheck en PostgreSQL

### Áreas de mejora

**Sin paginación en endpoints de listado**

- `GET /transacciones`, `GET /categorias`, `GET /perfil/metas` devuelven todas las filas sin límite. Con muchos datos esto será un problema de rendimiento.

**Sin frontend** -- el `docker-compose.yml` referencia un servicio `frontend` con directorio `./frontend` que no existe en el repositorio.

**Chat sin memoria conversacional** (`backend/app/services/chat_servicio.py`)

- Cada mensaje se procesa independientemente. No se envían mensajes previos al LLM, por lo que el asistente no tiene contexto de la conversación previa.

**`_columna_embedding()` se ejecuta en tiempo de importación** (`backend/app/models/knowledge.py:20-26`)

- La decisión SQLite vs pgvector se toma al importar el módulo, basándose en la variable de entorno. Esto funciona pero es frágil -- si el import ocurre antes de configurar env vars, genera un tipo de columna incorrecto.

# Análisis de Negocio: AI Financial Copilot con Motor de Oportunidades Contextuales

## De qué trata

El proyecto propone un copiloto financiero personal basado en IA que va más allá de las apps tradicionales de visualización de gastos. La idea central es construir un asistente que combine tres dimensiones: el **perfil financiero dinámico** del usuario (ingresos, gastos, objetivos, tolerancia al riesgo), el **contexto económico local** (instrumentos disponibles, variables macro, moneda) y un **motor de oportunidades** que recolecta y estandariza productos de inversión reales del mercado. Sobre esas tres capas, un mecanismo de matching evalúa compatibilidad y genera recomendaciones accionables y explicables: qué hacer, cuándo, con qué exposición y qué impacto tiene sobre las metas del usuario.

Arquitectónicamente se apoya en una capa de datos personales, una capa de datos de mercado, una capa de conocimiento tipo RAG, una capa de razonamiento con LLMs y orquestación de agentes, y una capa de decisión que produce salidas estructuradas. La evolución va de ingesta manual y recomendaciones simples, hacia integraciones automáticas, simulación de escenarios y eventualmente comportamiento proactivo con alertas en tiempo real.

## Fortalezas

La propuesta está bien posicionada conceptualmente. Identifica con precisión un gap real: las herramientas existentes son pasivas y genéricas, mientras los usuarios necesitan decisiones contextualizadas. La decisión de no hardcodear reglas por país y en su lugar derivar el contexto dinámicamente es elegante y hace al sistema escalable a múltiples mercados, algo especialmente relevante para LATAM donde la fragmentación regulatoria mata a muchos productos fintech. La insistencia en **explicabilidad como componente de primera clase**, no como afterthought, es acertada tanto por confianza del usuario como por requisitos regulatorios futuros. La arquitectura por capas es limpia y permite construir incrementalmente, y el uso de RAG para fundamentar recomendaciones reduce el riesgo de alucinaciones en un dominio donde eso sería catastrófico. Finalmente, el alcance escalonado (manual → automático → proactivo) es realista y permite validar valor antes de invertir en integraciones costosas.

## Riesgos

El riesgo más serio es **regulatorio**. En la mayoría de jurisdicciones, recomendar instrumentos específicos de inversión a un individuo cae bajo asesoría financiera regulada, lo que requiere licencias, cumplimiento de KYC/AML, y responsabilidad legal por las recomendaciones. El documento no aborda esto y es un blocker existencial, no un detalle. Ligado a esto está el riesgo de responsabilidad por malas recomendaciones: si un usuario pierde dinero siguiendo al copiloto, la exposición legal y reputacional es alta, especialmente si el sistema sugiere instrumentos volátiles.

El segundo riesgo es de **calidad y cobertura de datos de mercado**. Estandarizar instrumentos heterogéneos entre países, monedas y tipos de activo es un problema mucho más difícil de lo que el documento sugiere. No existen APIs unificadas para esto en LATAM, y construir y mantener esa capa puede consumir más recursos que el resto del producto junto. Relacionado: la ingesta de datos personales del usuario. La versión manual tiene fricción altísima y los usuarios abandonan; la versión automática requiere integraciones tipo open banking que en muchos mercados no existen o son inmaduras.

Hay también riesgo de **alucinación y razonamiento incorrecto del LLM** en cálculos financieros, donde un error numérico no es cosmético sino que destruye confianza. Y un riesgo más sutil: el **matching algorítmico oversimplificado**, donde reducir decisiones financieras complejas a atributos comparables (riesgo, liquidez, retorno esperado) puede ignorar correlaciones, contexto fiscal, y consideraciones de portafolio que un asesor humano sí captura.

## Consideraciones

Antes de construir, conviene definir si el producto es **asesor o educador**. Posicionarlo como herramienta educativa y de organización (no como recomendador) reduce drásticamente la exposición regulatoria y permite iterar más rápido, dejando la capa de "recomendación accionable" para una v2 con el marco legal resuelto. También vale la pena decidir el mercado inicial muy específicamente: lanzar en un solo país con una sola moneda y un set acotado de instrumentos, antes de presumir generalidad multi-país. La promesa de adaptabilidad sin configuración es atractiva pero arriesgada como punto de partida.

Sobre el stack técnico, conviene separar claramente lo que hace el LLM de lo que hace código determinístico: cálculos, proyecciones y matching deberían vivir en lógica auditable, no en el modelo. El LLM se reserva para interpretación, explicación y conversación. Esto también facilita testing y reduce riesgo regulatorio. La capa RAG necesita una estrategia clara de freshness para datos de mercado, y un mecanismo de citación que permita auditar de dónde salió cada afirmación.

## Viabilidad

**Técnicamente** es viable con tecnología actual: RAG, agentes, y orquestación de LLMs son suficientemente maduros, y la arquitectura propuesta es estándar. La parte no trivial es la ingeniería de la capa de datos de mercado y la integración con datos personales del usuario, que es más trabajo de plomería que de IA.

**Comercialmente** la viabilidad depende mucho del posicionamiento. Como herramienta de educación y organización financiera con sugerencias contextuales es muy viable y tiene un mercado claro, especialmente en LATAM donde la literacy financiera es baja. Como asesor de inversiones automatizado es viable solo con inversión significativa en compliance, partnerships con brokers regulados, o un modelo B2B2C donde el riesgo regulatorio lo absorbe una institución licenciada.

**En resumen:** la idea es sólida, la arquitectura es razonable, pero el proyecto se juega su viabilidad en dos cosas que el documento no aborda: el marco regulatorio y la realidad operativa de obtener datos de mercado e integrar datos personales. Recomendaría un MVP enfocado en un solo país, posicionado como copiloto educativo con sugerencias generales, validando engagement antes de invertir en la capa de recomendación específica de instrumentos.

# Tech Stack Recomendado

Stack pragmático, alineado con tecnologías existentes y que permite ir del MVP a una versión avanzada sin rewrites grandes.

## Frontend

**Next.js 15** (App Router) + TypeScript + Tailwind + shadcn/ui. Es el stack natural para un producto conversacional con dashboards. Para la parte de chat, **Vercel AI SDK** (`ai` package) maneja streaming, tool calls y estados de UI sin reinventar la rueda. Para visualizaciones financieras (gráficos de cashflow, proyecciones, breakdown de gastos) **Recharts** cubre el 90% de los casos; si se necesita algo más sofisticado, **Visx**.

## Backend y orquestación de agentes

La decisión clave es separar lo determinístico de lo no determinístico.

**Capa de razonamiento con LLM:** Python con **FastAPI** y **LangGraph** para orquestación de agentes. LangGraph encaja mejor que LangChain plano para este caso porque el flujo tiene estado (perfil del usuario, contexto de mercado, recomendación en construcción) y necesita pasos condicionales: "¿el usuario tiene capacidad de inversión? → si sí, buscar instrumentos; si no, sugerir ajuste de gastos". Eso se modela limpio como un grafo.

**Cálculos financieros** (proyecciones, cashflow, métricas de portafolio, matching scoring): Python puro, sin LLM. Bibliotecas como `numpy`, `pandas` y `numpy-financial` para cálculos, y código auditable con tests unitarios. **El LLM nunca debe hacer aritmética**, solo interpretar y explicar resultados de funciones determinísticas.

**Modelos:** Claude Sonnet 4.6 como caballo de batalla para razonamiento y generación de explicaciones, Claude Haiku 4.5 para clasificación, extracción estructurada y tareas de bajo costo (parseo de transacciones, categorización de gastos). Todo vía la Claude API con tool use para que el agente invoque las funciones financieras determinísticas.

## Capa de datos

**Supabase** (Postgres + Auth + RLS) para datos personales, transacciones, perfiles, objetivos e historial de recomendaciones. RLS es no negociable porque se manejan datos financieros privados. Para datos de series temporales pesadas (histórico de precios, indicadores macro) si crece mucho, una tabla particionada en el mismo Postgres alcanza al inicio; **TimescaleDB** si escala.

**Prisma** como ORM desde el lado de Next.js para operaciones CRUD del usuario, y **SQLAlchemy** o `asyncpg` desde el lado Python para los servicios de razonamiento.

## Capa RAG y conocimiento

**pgvector** sobre el mismo Supabase para embeddings. Evitar meter una vector DB separada al inicio: agrega operaciones, costo y latencia sin justificarse hasta que haya millones de chunks.

**Embeddings:** Voyage AI (`voyage-3-large` o `voyage-finance-2` que está específicamente entrenado para dominio financiero). Como fallback o alternativa, los embeddings de OpenAI.

**Pipeline de ingesta de conocimiento** (descripciones de instrumentos, contenido educativo, contexto macro): scripts Python con chunking semántico, metadata rica (país, tipo de instrumento, fecha) y reindexación periódica. LlamaIndex ayuda si se quiere acelerar el armado del pipeline; si no, LangChain plano alcanza.

## Datos de mercado

Esta es la capa más compleja operacionalmente. No hay una solución única, depende del mercado:

- **Precios de activos globales y FX:** Alpha Vantage, Twelve Data, o Yahoo Finance no oficial para empezar; Polygon.io si se necesita calidad institucional.
- **Datos macro:** Banco Mundial API, FRED (Fed de St. Louis), y para LATAM las APIs de bancos centrales locales (Banxico tiene API pública decente).
- **Instrumentos locales LATAM:** aquí toca scraping responsable o partnerships, porque APIs unificadas no existen.

Estructurar esto como un servicio independiente de ingesta con jobs programados (cron en un worker dedicado o **Inngest**, que maneja bien jobs de larga duración con reintentos). Los datos crudos van a Postgres normalizados a un esquema interno común de "instrumento financiero".

## Integración bancaria (fase futura)

Para LATAM: **Belvo** es el estándar de facto para open finance regional, cubre México, Colombia, Brasil y Chile. Empezar con ingesta manual (CSV upload + parser con Haiku) es lo correcto para validar; Belvo viene cuando haya tracción y presupuesto.

## Infraestructura y deployment

- **Vercel** para Next.js (frontend + API routes ligeras).
- **Railway**, Fly.io o Render para los servicios Python de razonamiento y los workers de ingesta; Railway es el más simple y suficiente hasta tener escala. Si más adelante se necesita más control, AWS ECS o Cloud Run.
- **Inngest** o Trigger.dev para jobs en background y workflows de larga duración (actualización diaria de mercado, regeneración de recomendaciones, alertas).
- **Observabilidad:** Langfuse o Helicone para tracing de llamadas a LLM (esencial para debuggear razonamiento de agentes y controlar costos). Sentry para errores de aplicación. PostHog para producto y analytics de uso.

## Pagos

**Stripe** cuando se llegue a monetización.

## Flujo de una recomendación (resumen)

> Usuario manda mensaje en el chat → Next.js streamea a un endpoint que llama al servicio Python → LangGraph arranca el grafo del agente → invoca tools determinísticas (calcular capacidad de ahorro, proyectar cashflow, consultar pgvector para contexto, query a tabla de instrumentos para candidatos) → Sonnet 4.6 sintetiza la recomendación con justificación → respuesta estructurada vuelve al frontend con streaming → se persiste en Supabase para historial y auditoría.

## Qué dejar fuera del MVP

Vector DB dedicada, message queue tipo Kafka, microservicios múltiples, Kubernetes, fine-tuning de modelos propios, integración bancaria automática, y cualquier framework de agentes "mágico" que abstraiga demasiado. Todo eso es deuda de complejidad que no paga renta hasta tener usuarios reales.

# Plan de Implementación Fase por Fase

Cinco fases con entregables concretos por cada una. Cada fase produce algo demostrable y usable, no infraestructura sin producto.

---

## Fase 0 -- Fundaciones y decisiones (semana 1)

Antes de escribir código, cerrar definiciones que evitan rework.

### Entregables

- **Documento de posicionamiento legal:** el producto se lanza como herramienta educativa y de organización financiera con sugerencias generales, no como asesor de inversiones. Esto define el lenguaje del producto, los disclaimers, y qué puede y no puede decir el agente.
- **Mercado inicial elegido:** México, una sola moneda (MXN), y un set acotado de categorías de instrumentos (cuentas de ahorro, CETES, fondos de inversión básicos, criptos majors). Todo lo demás queda fuera del MVP.
- **Repos creados:** monorepo con `apps/web` (Next.js) y `services/agent` (Python/FastAPI), o dos repos separados. Monorepo con pnpm workspaces + un `services/` aparte es la opción recomendada.
- **Supabase project creado**, con esquema inicial vacío pero con RLS habilitado por default en todas las tablas.
- **Cuenta de Anthropic API** con límites configurados, y cuenta de **Langfuse** para tracing desde el día uno.

### Decisión técnica clave

Definir el **contrato de datos del perfil financiero**. Un JSON schema versionado que describa qué es un usuario, una transacción, un objetivo, una recomendación. Todo el resto del sistema se construye sobre eso.

## Fase 1 -- MVP conversacional con perfil manual (semanas 2 a 5)

**Objetivo:** un usuario puede crear su perfil, registrar transacciones manualmente, y conversar con el copiloto sobre su situación. Sin recomendaciones de inversión todavía.

### Backend (Supabase + Next.js API routes)

- Schema de Postgres con tablas: `users`, `profiles`, `transactions`, `categories`, `goals`, `conversations`, `messages`. Todas con RLS por `user_id`.
- Auth con Supabase Auth (email + magic link, sin passwords para reducir fricción).
- API routes en Next.js para CRUD de transacciones y objetivos.
- Función determinística que calcule métricas básicas del perfil: ingresos mensuales, gastos por categoría, capacidad de ahorro, runway financiero. Estas métricas son las que el agente va a consultar como tools.

### Frontend (Next.js)

- **Onboarding:** 4 pantallas para capturar perfil base (ingresos, gastos fijos, objetivos, tolerancia al riesgo declarada).
- **Dashboard** simple con métricas clave y gráfico de cashflow del mes.
- **Pantalla de transacciones** con CRUD manual + upload de CSV. El parser de CSV usa Haiku 4.5 para mapear columnas heterogéneas al schema interno (primer uso de LLM del producto, resuelve fricción real).
- **Interfaz de chat** con Vercel AI SDK conectada al servicio del agente.

### Servicio de agente (Python + FastAPI)

- Endpoint `/chat` que recibe mensaje + `user_id`, recupera perfil del usuario desde Supabase, y responde con streaming.
- LangGraph con un grafo simple: nodo de análisis de intención → nodo de recuperación de datos del perfil (vía tool) → nodo de respuesta con Sonnet 4.6.
- Tools expuestas al modelo: `get_user_profile`, `get_recent_transactions`, `calculate_cashflow_projection`, `get_spending_breakdown`. Todas determinísticas, todas con tests.
- Tracing con Langfuse desde la primera llamada.

### Resultado

Un producto que un usuario real puede usar para entender mejor sus finanzas, conversar sobre patrones de gasto, y proyectar cuánto puede ahorrar. Ya es valioso por sí solo y se puede poner frente a 10-20 usuarios beta para validar engagement.

---

## Fase 2 -- Capa de conocimiento y contexto (semanas 6 a 8)

**Objetivo:** el agente deja de hablar genérico y empieza a fundamentar respuestas en conocimiento financiero específico de México.

### Pipeline RAG

- Script Python de ingesta que toma documentos curados manualmente: descripciones de instrumentos disponibles en México (CETES, fondos comunes, cuentas de ahorro de bancos principales, etc.), contenido educativo, glosario financiero. Empezar con 50-100 documentos curados es suficiente.
- Chunking semántico con metadata: tipo de instrumento, riesgo aproximado, liquidez, requisitos de acceso, fuente, fecha de actualización.
- Embeddings con `voyage-finance-2`, almacenados en pgvector en el mismo Supabase.
- Tabla `knowledge_chunks` con columnas para texto, embedding, metadata JSONB, y un índice ivfflat.

### Integración con el agente

- Nueva tool: `search_financial_knowledge(query, filters)` que hace búsqueda híbrida (vector + keyword sobre metadata).
- Nuevo nodo en el grafo de LangGraph: cuando la intención del usuario involucra una pregunta sobre instrumentos o conceptos, el agente consulta esta tool antes de responder.
- **Sistema de citas:** cada respuesta que use chunks debe incluir referencias verificables. Esto se renderiza en el frontend como tooltips o footnotes.

### Capa de datos macro (versión mínima)

- Job programado (Inngest o cron simple) que actualiza diariamente: tipo de cambio USD/MXN, tasa de referencia de Banxico, inflación reciente, tasa de CETES a 28 días. Todo desde la API pública de Banxico.
- Tabla `market_context` con snapshots diarios.
- Tool `get_current_market_context()` que el agente consulta cuando responde sobre rendimientos esperados o decisiones de timing.

### Resultado

El agente puede responder preguntas como "¿qué son los CETES y me convienen?" con información fundamentada, citada, y contextualizada al momento actual.

---

## Fase 3 -- Motor de oportunidades y matching (semanas 9 a 13)

Aquí es donde el producto empieza a diferenciarse de un chatbot financiero genérico.

### Modelo de instrumentos

- Schema unificado en Postgres para representar cualquier instrumento financiero: `instruments` con columnas para tipo, emisor, riesgo (escala normalizada 1-5), liquidez (días), rendimiento histórico, rendimiento esperado, monto mínimo, requisitos de acceso, moneda, jurisdicción.
- Pipeline de ingesta de instrumentos: empezar con un set curado a mano (20-30 instrumentos principales del mercado mexicano), después automatizar fuentes específicas. No intentar generalidad multi-país aquí.
- Job de actualización de rendimientos y precios.

### Motor de matching (todo determinístico, sin LLM)

Módulo Python `matching/` con funciones puras:

- `calculate_investment_capacity(profile)` → cuánto puede invertir el usuario sin comprometer su runway.
- `score_instrument_for_user(instrument, profile)` → score 0-1 basado en alineación de riesgo, horizonte temporal, liquidez requerida, monto disponible.
- `rank_opportunities(user_id, top_k)` → devuelve los mejores instrumentos para ese usuario con score y razones estructuradas.

Tests unitarios extensivos. Esto es lógica financiera y no puede tener bugs sutiles.

### Integración con el agente

- Nueva tool: `find_opportunities_for_user()` que invoca el motor de matching.
- Nuevo flujo en LangGraph: cuando el usuario pregunta "¿qué puedo hacer con mi dinero?" o el agente detecta capacidad de inversión no utilizada, ejecuta el motor, recibe candidatos rankeados con razones, y los presenta con explicación generada por Sonnet 4.6 a partir de las razones estructuradas.
- **Salida estructurada de recomendación:** un JSON con instrumento sugerido, monto, razonamiento, riesgos, alternativas. Se persiste en `recommendations` para auditoría e historial.

### Frontend

- Nueva sección **"Oportunidades"** que lista las recomendaciones generadas con expandibles para ver el razonamiento completo.
- Cada recomendación tiene disclaimers visibles consistentes con el posicionamiento educativo definido en Fase 0.

### Resultado

El producto core funcionando. Un usuario carga sus datos, conversa con el copiloto, y recibe sugerencias específicas y explicadas alineadas a su situación.

## Fase 4 -- Proactividad, simulación e integraciones (semanas 14 a 20)

Iterando sobre un producto vivo con usuarios reales. Prioridades dependen del feedback.

### Simulación de escenarios

- Función determinística que toma el perfil y simula proyecciones a 1, 5, 10 años bajo distintas estrategias.
- Tool del agente que el usuario puede invocar conversacionalmente: "¿qué pasa si invierto 5000 al mes en CETES?".
- Visualización de proyecciones en el frontend con Recharts.

### Sistema proactivo

- Job nocturno que evalúa cada usuario activo: detecta cambios en el perfil (ingreso extra, gasto inusual, capacidad de inversión nueva), revisa si hay oportunidades que antes no aplicaban, y genera alertas.
- Notificaciones por email (Resend) o push si hay app móvil eventualmente.

### Integración con datos reales

- **Belvo** para México: open finance que conecta cuentas bancarias y trae transacciones automáticamente. Reemplaza el upload manual de CSV.
- Requiere KYC más serio del usuario y vale la pena solo cuando ya se validó que la gente paga.

### Mejoras al motor de razonamiento

- **Memory persistente del agente:** además del perfil, el agente recuerda preferencias expresadas en conversaciones previas (tolerancia real al riesgo observada vs declarada, rechazos a tipos de instrumentos, etc.).
- **Feedback loop:** el usuario marca recomendaciones como útiles o no, y eso entra al contexto del agente para futuras sugerencias.

## Notas transversales

### Testing

Toda la lógica financiera determinística necesita cobertura alta de tests unitarios desde el día uno. Para el agente, usar Langfuse para grabar trazas reales y construir un set de evaluación con ~30-50 conversaciones canónicas que se corren en CI cada vez que cambian prompts o el grafo. Esto evita regresiones silenciosas que son brutales en productos LLM.

### Costos de API

- **Sonnet 4.6** para razonamiento principal.
- **Haiku 4.5** para clasificación de intención, parsing de CSVs, categorización de transacciones, y cualquier tarea de extracción.
- La regla: si el output es estructurado y la tarea es acotada, Haiku. Si requiere razonamiento multi-paso o explicación al usuario, Sonnet. Esto puede ser la diferencia entre quemar $500/mes en API o $2,000.

### Seguridad

- RLS en Supabase desde el primer día.
- Secrets en variables de entorno gestionadas por Vercel y Railway (nunca en código).
- Nunca pasar datos sensibles del usuario al LLM más allá de lo estrictamente necesario para la tarea.

### Sobre el orden real

Las semanas son orientativas trabajando con dedicación parcial. Si se trabaja full time, Fase 1 es 2 semanas y la Fase 3 cae a 3. Lo importante no son las fechas sino el orden de las dependencias.

### Recomendación concreta para arrancar

Cerrar la Fase 0 en dos días (decisiones de mercado, posicionamiento y schema de datos), y el resto de la semana empezar Fase 1 con el setup del repo, Supabase y el primer endpoint de chat funcionando contra Sonnet sin tools. Esto da un loop cerrado mínimo sobre el cual iterar todo lo demás.
